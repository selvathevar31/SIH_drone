## 2. Telemetry Data Contract
A strict JSON contract is established under `/api/telemetry/hardware`. Null values must be sent explicitly on sensor failure. The backend verifies coordinate bounds and logical constraints (e.g., PM2.5 >= 0) and rejects impossible readings.

## 3. ESP32 Responsibilities
The ESP32 is strictly responsible for:
- Reading environmental payloads (PMS2.5, DHT11).
- Consuming ArduPilot MAVLink telemetry for spatial correlation.
- Fusing and pushing authenticated data (via `X-Hardware-Token`) to the backend.

## 4. ArduPilot Responsibilities
ArduPilot handles all critical flight parameters, waypoint navigation, and safety overrides. The ESP32 does not command the drone. Recommendations generated by the AI Dashboard remain read-only.

## 5. Backend Changes
- Added `/api/telemetry/hardware` API route (`app/routes/hardware.py`).
- Implemented HTTP Header Authentication for telemetry.
- Enforced hard `data_source = "hardware"` override to prevent source spoofing.

## 6. Firmware Changes
Created `firmware/esp32_telemetry_stub/README.md` to guide the engineering team on data loop structures, handling offline states, and dropping payloads when GPS fix is missing.

## 7. Electrical Safety Findings
**CRITICAL RISKS IDENTIFIED:**
1. **ESP32 Power Rail:** The proposed 5V BEC must NOT be connected to the ESP32 `3.3V` pin. It must only connect to the `VIN/5V` pin to utilize the onboard LDO.
2. **PMS2.5 & MQ-7 Signal Rails:** These 5V sensors will output 5V logic/analog signals. Connecting them directly to the ESP32 GPIOs will destroy the microcontroller. **Voltage dividers (e.g. 10k/20k) are mandatory.**

## 8. Sensor Validation Status
- DHT11: Validated.
- PMS2.5: Validated via API structure. Requires physical voltage division.
- MQ-7: **Unvalidated**. The hardware is present but software support is explicitly disabled due to complex analog heater requirements.

## 9. Real vs Simulated Data Flow
- **Real:** ESP32 → `/api/telemetry/hardware` → Database (`data_source: "hardware"`)
- **Simulated:** Simulator Dashboard → `/api/missions/{id}/response/simulate` → Database (`mission_id: SIM_RES-{id}`)
- Isolation is absolute. Simulation data cannot spoof hardware data, and hardware data ingestion enforces source tagging.

## 10. Test Results
- Implemented `backend/tests/test_hardware_telemetry.py` to verify ingestion logic.
- Verifies: GPS failure handling (422 Unprocessable), Impossible PM values (422 Unprocessable), Unauthorized tokens (401), and successful ingestion (201).

## 11. Known Limitations
- The MQ-7 sensor is not supported by this phase's software contract.
- Physical integration relies on network stability; the ESP32 currently has no onboard SD-card caching implemented in the stub if the backend becomes unreachable during flight.
